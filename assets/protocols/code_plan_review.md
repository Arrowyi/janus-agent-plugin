## Protocol: code_plan_review

Apply this card in two stages: Stage 1 reviews a `plan.md` before implementation; Stage 2 reviews the whole task's final patch after all milestones land. The same card governs every single-milestone patch review in between. Report only correctness-affecting problems.

Input — by review shape, supplied verbatim by the dispatcher; read external state files only at the exact supplied paths (never `read` or `glob` a parent data root), and report any input that is neither supplied nor explicitly declared `none (<reason>)` in `unresolvedGaps` with `resolved: false`, never reconstructed from the diff alone:

- Stage 1 (plan): the exact `plan.md` path, the exact accepted `design.md` path (or `design.md: none (standalone plan; approved design-gate baseline in plan.md)` with the approved design-gate text and exact file list), and the target repository paths.
- Single-milestone patch: the `.review-mK.patch` path (or `.review-mK-rN.patch` on a fix round) with its metadata header and tail sentinel, the exact `plan.md` path (or `plan.md: none (L0 micro-change; approved inline baseline attached)`), the exact accepted `design.md` path (or `design.md: none (no design record)`), the verbatim baseline excerpt naming the milestone's end state and `Confirmed paths`, the executor's actual verification output, `reviews_job_ids`, and — on a fix round — the previous round's issue list.
- Stage 2 (final): the .review-final.patch path (plus .review-final-rN.patch and the previous round's issue list on a Stage-2 repair round) with its header and sentinel, the exact plan.md path (with its completed ledger and any `debt: [...]` entries), the exact design.md path (or `design.md: none (approved design-gate baseline in plan.md)`), the final full-suite verification output, `git status --porcelain --untracked-files=all`, and `reviews_job_ids`.

Stage 1 — plan review:

1. Map each accepted decision in the baseline to a task in `plan.md`; a decision with no task is a missing task. Check the repo's `AGENTS.md` change-verification and co-change rules: any required companion file, generated-artifact check, or verification command omitted from `plan.md` or `Confirmed paths` is a missing task or scope gap.
2. Map each interface or contract to a test; an interface with no test is an untested interface.
3. Check migration, compatibility, idempotency, concurrency, transaction, and failure-path coverage where the design names them.
4. Check that verification output supports the claims in the plan; an unrun command is not evidence.
5. Check that the plan is revertible in order, that a failed step has a safe stopping point, and — by inspecting the target source and its call or import dependencies (via host code-graph tools confirmed in current source, or targeted `read`/`grep`) — that each milestone's `Confirmed paths` is closed under planned signature or contract changes (independently green at the milestone boundary, rejecting any plan where a non-final milestone's verification depends on an `AGENTS.md`/`CLAUDE.md` edit reserved for the final milestone) and reserves preparatory-refactor scope when touched sites carry existing structural decay.

Stage 2 — diff review (substantive correctness and contract defects only):

6. Check the diff stays inside the updated `Confirmed paths` and the accepted decisions; unrelated edits are scope creep, while contract-preserving preparatory refactoring and verified dead-helper removal inside `Confirmed paths` are net code-health improvements. Close the loop on boundary, null, and error handling; on concurrency, idempotency, and migration safety; on interface compatibility; and on tests that actually prove the change. In Round 1, read `design.md` (when present), `plan.md`, `AGENTS.md`, and the surrounding module code of the touched files from the exact supplied paths — never `read` or `glob` `$XDG_DATA_HOME/janus-agent` or `<designStateDir>` themselves — and trace the integrated diff's callers and callees with host code-graph tools confirmed against current source, or targeted `read`/`grep`. The narrowed non-final milestone carve-out: `AGENTS.md`/`CLAUDE.md` edits reserved for the final milestone and distinct tasks scheduled in later milestones `M_{k+1..n}` are not `M_k` missing tasks, provided `M_k` is independently green with no broken callers, stale required generated artifacts, or red verification at the `M_k` boundary.
Structural defects count too: hand-edited generated output breaking the single source of truth, a query hiding side effects, swallowed exceptions masking failures, one conceptual change missed across synchronized sites, or compounded tactical decay in touched code (bolting a fragile kludge onto third-instance knowledge duplication, tangled branching, or leaky boundaries where an in-scope preparatory refactor or a `Scope-Expansion` Report-Up was required, or deleting a shim still referenced by an external caller, public export, config, or persisted schema). Prefix any compounded-decay finding in `correctnessRisks` with `"[structural] "`, naming a concrete failure or maintenance hazard and one actionable in-scope direction (or noting `Scope-Expansion` is required).
Apply three convergence gates: (a) when the working, tested implementation and an alternative are equally sound under the shared Engineering Principles, the working code wins (`verdict: "pass"`, optional note in `residualUncertainty`);
(b) raise `[structural]` findings on touched code in Round 1 (`.review-mK.patch` or Stage-2 Round 1 `.review-final.patch`), while fix rounds (`.review-mK-rN.patch` or `.review-final-rN.patch`) verify prior-round items closed and check only modified fix hunks for regressions or new decay introduced by the fix itself — never raising a new blocking finding, whether `"[structural] "` or an ordinary correctness or call-chain demand, on code untouched since Round 1 unless a fix hunk itself broke an untouched caller or contract, routing any newly noticed concern on untouched code non-blockingly to `residualUncertainty`, and never reversing a followed Round-1 direction;
(c) when the in-scope change is sound (not a kludge) but exposes pre-existing decay outside `Confirmed paths` or an accepted `design.md` contract, return `pass` and record the cross-file debt in `residualUncertainty` — and in Stage 2, mechanically reconcile every `debt: [...]` entry in `plan.md`'s completed ledger: a debt explicitly scheduled for closure in a later milestone is verified closed (a skipped scheduled task goes to `missingTasks`), while any other entry is carried forward into Stage 2's `residualUncertainty` without overturning earlier convergence-gate passes — never suppressing an independent Stage-2 correctness finding when the integrated diff itself leaves a caller, contract, or verification check broken.
Style preferences never gate the verdict.
7. Review the test surface with the supplied baseline increments — `git status --porcelain --untracked-files=all`, the code and test diffs, and the test-run output: welcome test updates that stay assertion-equivalent through a refactor or signature change (or disclosed one-line removal of a test exclusive to a deleted dead internal helper); a removed or `.skip`/`.only`-parked test, a thinned-out assertion, a test-configuration edit that silences a failure, or an untracked new test file the runs never covered is a correctness risk, not style.
8. Return `codePlanReview` with `verdict` (`pass` / `revise` / `block`), `deviations`, `missingTasks`, `untestedInterfaces`, `correctnessRisks`, `scopeCreep`, and `residualUncertainty`; set `resolved: true` only when no correctness-affecting problem remains.

Patch integrity gates — every `.review-mK.patch`, `.review-mK-rN.patch`, and `.review-final.patch` review:

9. Confirm the tail sentinel (`=== EOF .review-mK.patch ===`, `=== EOF .review-mK-rN.patch ===`, `=== EOF .review-final.patch ===`, or `=== EOF .review-final-rN.patch ===`) was reached; when the header reports `total_lines > 1800`, read in windows until the sentinel.
10. When `long_line_files` in the header is non-empty, only added (`+`) or context lines longer than 2000 characters evade line-truncating reads and leave the patch not fully readable: return `revise` or `block`, never `pass`. An overlong deletion (`-`) line is content the patch removes: it stays disclosed in `long_line_files` and does not by itself block `pass` — verify instead that the controller's verification output attests the end-state file contains no line over 2000 characters, and without that attestation report the gap as unresolved.
11. A missing sentinel or a malformed header is a reported gap with `resolved: false`.
